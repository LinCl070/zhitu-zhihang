# 职途智航 Web App 前端设计文档

> 文档用途：提供给 Open Design 或前端设计/实现人员，作为 Web App 视觉与交互改造的唯一设计输入。
>
> 项目名称：职途智航
>
> 产品类型：高校就业择业规划 Web App
>
> 目标：在不改变现有业务接口和数据治理边界的前提下，重做前端应用壳、信息层级、角色工作台和状态反馈。

## 1. 先明确产品性质

职途智航不是宣传网站、品牌落地页或营销型首页，而是一个供学生、就业指导教师和就业管理员使用的业务 Web App。

设计重点不是“首屏是否有冲击力”，而是：

- 用户能否快速知道自己当前处于哪个角色和工作阶段；
- 用户能否在一个稳定的应用壳中完成连续任务；
- 学生能否理解岗位推荐的依据、缺口和下一步；
- 教师能否只看到授权范围内的学生摘要并提交指导意见；
- 管理员能否查看授权、岗位、资料和脱敏审计状态；
- 加载、空数据、失败、保存成功和转人工等状态是否明确；
- 页面在桌面端和窄屏端是否仍然可操作。

因此，本次改造必须遵守以下原则：

1. 以应用结构优先于装饰风格。
2. 以任务流和信息扫描优先于大幅 Hero 区域。
3. 以角色权限和数据来源优先于炫技动效。
4. 以真实业务内容优先于占位文案和虚构模块。
5. 以最小改动复用现有 API、组件和数据结构。

## 2. 当前前端基线

当前前端位于 `frontend/`，技术栈为 React + TypeScript + Vite，图标使用 `lucide-react`。

主要入口：

- `frontend/src/App.tsx`：学生端、登录入口、学生视图切换、会话状态和 API 调用。
- `frontend/src/StaffDashboard.tsx`：教师工作台和管理员工作台。
- `frontend/src/styles.css`：全局样式和响应式规则。
- `frontend/src/api/client.ts`：前端业务 API 类型和请求封装。
- `frontend/src/config/brand.ts`：产品名和学校名称。

### 2.1 现有角色

#### 学生

学生端目前包含四个业务视图：

1. 职业画像
2. 岗位推荐
3. 行动计划
4. 就业咨询

学生画像字段包括：

- 专业
- 技能标签
- 脱敏项目摘要
- 目标岗位
- 目标城市
- 当前求职阶段

岗位推荐包含：

- 匹配总分
- 技能、专业、项目、城市、目标岗位分项分数
- 待补强技能
- 岗位标题和单位
- 模拟/公开岗位标识
- 来源标题、链接、发布日期和有效期

行动计划包含：

- 计划状态
- 阶段
- 优先级
- 具体任务

就业咨询包含：

- 问题输入
- 智能建议
- 模拟/真实返回状态
- 免责声明
- 建议转人工提示

#### 教师

教师只能看到已授权学生的摘要，当前内容包括：

- 授权学生列表
- 学生姓名、专业、目标岗位、目标城市和求职阶段
- 行动计划数量
- 已提交指导意见数量
- 指导意见表单
- 历史指导意见及时间

教师端不应展示学生技能、项目原文或未授权信息。

#### 管理员

管理员工作台目前包含：

- 教师-学生授权范围配置
- 模拟岗位审核状态表
- 知识资料台账
- 脱敏审计事件表
- 资料、岗位和审计数量概览

管理员不应展示完整学生画像、教师意见正文、平台密钥或数据库连接信息。

## 3. 改造目标

### 3.1 总体方向

采用“可信的任务型业务工作台”作为总方向：

- 保留现有森林绿、米白、珊瑚色的可信基因；
- 去掉营销网站式的大面积留白、超大标题和装饰性网格；
- 建立统一 App Shell；
- 让每个页面都有明确的当前任务、数据状态和下一步动作；
- 学生、教师、管理员共用基础设计语言，但拥有不同的导航和信息密度。

### 3.2 不做什么

本次设计不包含：

- 新增自动投递、招聘沟通或录用预测功能；
- 接入真实学校数据库；
- 新增真实认证系统；
- 修改后端 API 和数据库模型；
- 引入大型 UI 框架或新的状态管理库；
- 把学生端改成营销首页；
- 用动画、渐变、3D 或插画掩盖信息架构问题。

## 4. 推荐的应用信息架构

### 4.1 统一 App Shell

桌面端结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 品牌 / 当前角色        当前工作区标题       环境状态 / 用户菜单 │
├───────────────┬──────────────────────────────────────────────┤
│               │ 页面上下文                                     │
│ 角色导航       │ 页面标题 + 状态 + 主操作                        │
│               │ ───────────────────────────────────────────── │
│ 主要入口       │ 内容区：表单 / 列表 / 卡片 / 表格 / 时间线         │
│               │                                                │
│ 辅助说明       │                                                │
└───────────────┴──────────────────────────────────────────────┘
```

移动端结构：

```text
┌────────────────────────────┐
│ 品牌 / 页面标题 / 角色菜单    │
├────────────────────────────┤
│ 页面内容                     │
├────────────────────────────┤
│ 底部四项角色导航              │
└────────────────────────────┘
```

### 4.2 顶部栏

顶部栏只放应用上下文，不做宣传：

- 产品名：职途智航
- 学校：成都信息工程大学
- 当前角色：学生演示、教师演示或管理员演示
- 当前环境：模拟模式
- 数据边界提示：脱敏演示、仅展示模拟岗位等
- 用户名和“切换角色”操作

顶部栏不使用大幅宣传语，不放多余的装饰图形。

### 4.3 学生导航

保留现有四个核心入口，避免为了“完整产品”强行增加页面：

1. 职业画像
2. 岗位推荐
3. 行动计划
4. 就业咨询

导航项应支持：

- 当前激活状态；
- 岗位推荐数量徽标；
- 画像未完成时的待处理提示；
- 行动计划存在时的进行中提示；
- 小屏幕下转为底部导航。

### 4.4 教师导航

教师端不应继续像学生端一样只依赖一块长页面。建议使用同一 App Shell，导航为：

1. 授权学生
2. 当前学生摘要
3. 指导意见

当前实现可以先保留单页结构，但视觉上必须把左侧学生列表和右侧详情明确为“列表-详情”工作区。

### 4.5 管理员导航

管理员导航为：

1. 权限配置
2. 岗位资料
3. 知识资料
4. 脱敏审计

管理员页以表格和状态为主，不要使用学生端的大卡片比例。

## 5. 三个可供 Open Design 探索的风格方向

建议让 Open Design 在同一份业务内容上做三个可切换变体，而不是生成三个无关页面。

### 方向 A：任务驱动工作台（首选）

关键词：当前阶段、下一步、进度、行动。

适合学生端，也能扩展到教师端。

视觉特征：

- 左侧窄导航，显示四个阶段和状态点；
- 顶部显示当前阶段，例如“准备求职”；
- 页面顶部用小型状态条显示画像完成度、推荐数量和计划状态；
- 岗位卡片把“匹配分”和“下一步生成计划”放在同一视觉层级；
- 缺口直接变成行动提示，而不是只作为红色文字；
- 行动计划使用轻量时间线或阶段列表；
- 动效仅用于状态变化，不用于首屏炫技。

优点：学生容易理解“我现在在哪一步、下一步做什么”。

风险：如果过度强调进度，会让教师和管理员页面显得过于像任务清单。

### 方向 B：可信校园工作台

关键词：克制、清晰、权限、来源、状态。

适合学校演示和正式业务场景。

视觉特征：

- 米白或浅灰背景，白色内容面板；
- 森林绿作为主操作色，珊瑚色只用于提醒和关键缺口；
- 统一使用状态标签：模拟、公开、待完善、已保存、进行中、需人工确认；
- 来源、有效期和数据边界固定出现在卡片或表格底部；
- 管理员表格清晰、紧凑、可快速扫描；
- 圆角较小，阴影很轻，减少“营销组件”感觉。

优点：最符合高校就业指导、权限治理和可追溯要求。

风险：如果信息层级不够强，可能显得像普通后台。

### 方向 C：证据审阅工作台

关键词：证据、拆解、对照、审核、审计。

适合岗位推荐、管理员和教师协助场景。

视觉特征：

- 岗位推荐采用“总分 + 分项证据 + 缺口 + 来源”的纵向结构；
- 分项评分使用小型条形指示或数字标签，不使用夸张图表；
- 支持展开岗位详情，查看匹配理由和来源信息；
- 管理员表格强化列标题、状态筛选和时间信息；
- 教师端突出“学生当前状态”和“待指导事项”；
- 页面整体比方向 A 更紧凑，适合桌面端。

优点：最能体现项目的规则匹配、来源可追溯和治理边界。

风险：学生端可能显得偏审计，不够轻松。

### 推荐组合

建议最终采用：

```text
方向 B 作为全局视觉基础
      +
方向 A 作为学生端任务导航
      +
方向 C 作为岗位证据和管理员表格的局部模式
```

这不是三套风格同时堆叠，而是：

- 一个统一的可信 App Shell；
- 学生端偏任务导向；
- 岗位和治理区域偏证据导向；
- 所有角色共享颜色、字体、状态和组件规则。

## 6. 视觉设计系统

### 6.1 色彩

保留现有色彩基因，但降低装饰性使用：

```css
:root {
  --app-bg: #f4f6f1;
  --surface: #ffffff;
  --surface-muted: #f7f8f5;
  --text: #18332d;
  --text-muted: #66756f;
  --border: #d9e0d8;
  --primary: #0b6956;
  --primary-strong: #075043;
  --primary-soft: #e8f2ed;
  --warning: #c56a42;
  --warning-soft: #fff1e9;
  --success: #267653;
  --success-soft: #e7f3ea;
  --info: #47728a;
  --info-soft: #edf4f7;
  --danger: #b34c43;
}
```

使用规则：

- 森林绿：主按钮、激活导航、成功状态、主要链接；
- 珊瑚色：缺口、待处理、人工确认提醒；
- 米白/浅灰：页面底色和次级区域；
- 不使用大面积渐变；
- 不使用高饱和紫色、霓虹色或科技蓝作为主色；
- 不用红色表示普通的能力缺口，只有真正错误才使用危险色。

### 6.2 字体

- 中文正文：系统无衬线字体，例如 Microsoft YaHei、Noto Sans SC。
- 页面标题：可以保留轻微的人文感，但不再使用过大的杂志式 serif 标题。
- 数据、分数和日期：使用清晰的无衬线数字。
- 不使用超过两种字体体系。

建议字号：

```text
页面标题：24–30px
区块标题：18–22px
正文：14–15px
辅助信息：12–13px
表格：12–14px
```

### 6.3 间距和密度

- 基础间距单位：4px；
- 页面内边距：桌面端 24–32px，窄屏端 16px；
- 卡片内边距：16–20px；
- 表格行高：44–52px；
- 表单字段间距：16–20px；
- 学生端保持中等密度；
- 管理员端允许更高密度；
- 不用大面积空白把内容推到页面底部。

### 6.4 圆角、边框和阴影

- 面板圆角：8–12px；
- 输入框圆角：6–8px；
- 标签圆角：999px 或 4px，按语义选择；
- 边框优先于阴影表达层级；
- 阴影只用于弹层、浮动菜单和明确悬浮状态；
- 不使用厚重玻璃拟态或卡片堆叠。

## 7. 核心页面设计

### 7.1 学生端：职业画像

页面目标：让学生完成最小必要信息，并理解保存后会触发岗位推荐。

布局：

- 页面顶部：`职业画像`、保存状态、简短说明；
- 主区：表单分成“基础方向”和“求职准备”两组；
- 右侧或顶部状态区：画像完成度、已填写字段数量、数据边界说明；
- 底部固定主操作：保存职业画像；
- 保存过程中按钮进入 loading；
- 保存成功后给出明确反馈，并自动切换到岗位推荐；
- 匹配失败时保留已保存画像，不清空表单。

表单分组建议：

```text
基础方向
  专业
  目标岗位
  目标城市

求职准备
  技能标签
  脱敏项目摘要
  当前求职阶段
```

不要新增家庭背景、性别、籍贯、健康、联系方式等字段。

### 7.2 学生端：岗位推荐

页面目标：让学生理解“为什么推荐”和“还差什么”。

顶部：

- 当前画像摘要；
- 推荐数量；
- 生成推荐按钮；
- 数据范围提示：已发布、未过期、公开或模拟岗位。

岗位卡片结构：

```text
┌─────────────────────────────────────────────────────────┐
│ 86  匹配分       后端开发实习生             生成行动计划 │
│                 成都示例科技 · 模拟岗位                  │
├─────────────────────────────────────────────────────────┤
│ 技能 42   专业 18   项目 12   城市 5   目标 9             │
├─────────────────────────────────────────────────────────┤
│ 待补强：Docker、Redis                                    │
├─────────────────────────────────────────────────────────┤
│ 来源：模拟岗位来源   有效至：2026-09-30                  │
└─────────────────────────────────────────────────────────┘
```

交互：

- 点击岗位卡片可展开匹配依据；
- 缺口可直接作为“生成行动计划”的输入说明；
- 来源链接在新标签页打开；
- 已过期或来源缺失的岗位不展示为推荐；
- 没有结果时显示原因和恢复动作，不只显示空白；
- 生成中显示按钮状态和页面级提示。

### 7.3 学生端：行动计划

页面目标：把匹配缺口变成可执行任务。

建议使用阶段列表，而不是厚重时间线：

```text
进行中

01  本周 · 高优先级
    补充 Redis 基础练习并整理项目说明

02  下周 · 中优先级
    完成一轮后端面试题与模拟面试
```

计划顶部显示：

- 关联岗位；
- 计划状态；
- 生成时间；
- 教师指导意见数量。

如果没有计划，显示“先从岗位推荐中选择一个岗位”，并提供返回推荐的按钮。

### 7.4 学生端：就业咨询

页面目标：提交问题，清楚区分智能建议和人工确认。

设计要求：

- 文本输入区域有示例问题；
- 提交按钮贴近输入区；
- 返回后以回答卡展示建议；
- 显示资料状态、来源和免责声明；
- `handoff_recommended` 时使用明确但不恐吓的人工确认提示；
- 模拟模式要显眼但不能抢过回答内容；
- 不伪装成确定性的录用或资格判断。

### 7.5 教师端

采用经典列表-详情工作区：

左侧：

- 已授权学生列表；
- 学生姓名；
- 专业和目标岗位；
- 求职阶段状态。

右侧：

- 学生职业摘要；
- 行动计划数量；
- 已提交意见数量；
- 指导意见输入框；
- 已提交意见历史。

教师端需要强调：

- “仅显示已授权学生”；
- “不展示技能、项目原文和敏感信息”；
- 提交指导意见后产生审计记录。

### 7.6 管理员端

管理员采用数据工作台风格，不使用学生端大卡片比例。

顶部概览只保留三个必要数字：

- 资料台账数量；
- 模拟岗位数量；
- 审计事件数量。

权限配置区：

- 教师选择框；
- 学生选择框；
- 授予访问范围按钮；
- 成功/失败提示。

表格区：

- 岗位资料；
- 知识资料；
- 脱敏审计。

表格规则：

- 表头固定层级；
- 状态使用标签，不直接依赖颜色；
- 日期统一格式；
- 长文本截断并支持查看详情；
- 窄屏时允许横向滚动，但页面本身不能横向溢出；
- 不显示完整画像、意见正文、密钥和连接信息。

## 8. 状态设计

所有业务页面必须定义以下状态：

### 初始状态

- 未登录：显示三个演示入口；
- 无画像：提示先建立职业画像；
- 无推荐：提示保存画像后生成推荐；
- 无计划：提示从岗位推荐进入；
- 无授权学生：提示管理员配置教师授权范围。

### 加载状态

- 登录中；
- 保存画像中；
- 生成推荐中；
- 生成行动计划中；
- 咨询中；
- 教师学生列表加载中；
- 管理员总览加载中。

加载状态要求：

- 按钮文字变化；
- 禁止重复提交；
- 页面不跳动；
- 不使用无意义的全屏转圈遮挡已有内容。

### 成功状态

- 画像已保存；
- 推荐结果已生成；
- 行动计划已生成；
- 指导意见已保存并记录审计；
- 教师访问范围已更新。

成功提示应说明发生了什么，并指出下一步，而不是只显示“成功”。

### 错误状态

- API 不可用；
- 画像校验失败；
- 画像缺失导致无法匹配；
- 推荐生成失败；
- 权限不足；
- 咨询资料不足。

错误提示要求：

- 使用用户可理解的中文；
- 保留已经成功保存的数据；
- 提供可恢复动作，例如重试、返回画像或联系教师；
- 不展示原始堆栈、密钥、工作流 ID 或数据库信息。

## 9. 交互和可访问性要求

- 所有按钮使用真实 `<button>`；
- 所有输入框拥有可见标签；
- 焦点状态清晰；
- 键盘可以完成导航、提交和展开；
- 颜色不能作为唯一状态信息；
- 图标必须配合文字或可访问名称；
- 小屏幕下导航和按钮仍可点击；
- 表格在窄屏幕下可横向滚动，不造成整个页面横向溢出；
- 文字行高保持 1.5 左右；
- 不使用自动播放动效或闪烁提示。

## 11. Open Design 原型验收标准

### 必须满足

- [ ] 视觉结果明显是 Web App，而不是落地页。
- [ ] 存在稳定的侧边导航或移动底部导航。
- [ ] 顶部能看到当前角色、环境和用户上下文。
- [ ] 学生、教师、管理员有不同但一致的工作台结构。
- [ ] 学生四个流程可被理解为连续任务。
- [ ] 岗位推荐显示总分、分项分数、缺口和来源。
- [ ] 教师只看到授权学生摘要。
- [ ] 管理员能够扫描授权、岗位、资料和审计信息。
- [ ] 有明确的空、加载、成功、错误和人工确认状态。
- [ ] 页面使用中文真实内容，不出现 lorem ipsum。
- [ ] 窄屏幕下页面可操作，无整体横向溢出。
- [ ] 视觉重点是信息结构和操作，不是装饰。

### 不应出现

- [ ] 营销式 Hero 标题。
- [ ] 超大 serif 标题占据主要屏幕。
- [ ] 装饰性网格背景成为主要视觉元素。
- [ ] 与就业规划无关的图片、插画或概念图。
- [ ] 虚构的招聘承诺、录用概率或敏感画像字段。
- [ ] 只展示静态截图、没有交互的三个页面。
- [ ] 将教师和管理员强行设计成学生端的复制品。

## 12. 实施边界

如果后续把设计落回当前仓库，建议按以下最小顺序实施：

1. 先重做全局 App Shell 和设计 token，不改变 API。
2. 再重做学生导航、页面标题和状态反馈。
3. 再优化岗位卡片和行动计划展示。
4. 再统一教师端列表-详情布局。
5. 最后压缩管理员表格和权限配置布局。
6. 每一步只做对应页面的可运行检查，不重写业务逻辑。

优先复用现有：

- `lucide-react` 图标；
- `api/client.ts` 类型和请求方法；
- `App.tsx` 中已有的业务回调；
- `StaffDashboard.tsx` 中已有的教师和管理员数据结构。

不要为了视觉改造引入新的 UI 框架、路由系统、状态管理库或图表库。

## 13. 最终推荐

最终建议不是选择一个孤立的“网站风格”，而是确定一套应用设计语言：

> **可信校园 Web App：以统一工作台为基础，以任务驱动组织学生流程，以证据审阅组织岗位和治理信息。**

这套方向最适合当前项目，因为它同时覆盖：

- 学生的连续求职任务；
- 教师的授权协助；
- 管理员的资料和审计；
- 项目强调的可解释匹配、隐私边界和来源追溯。
